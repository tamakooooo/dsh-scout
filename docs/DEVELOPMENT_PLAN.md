# 招聘插件：岗位独立配置、网站自主适配与多窗口筛选

版本：v0.6 自主适配版  
日期：2026-10-01

已确认需求：做成插件；岗位和招聘条件可单独设置；agent 自主识别与适配招聘网站及其改版；快速筛选合适简历，符合条件后自动打招呼，留下简单记录，支持多个窗口并行。继续采用一次任务授权、范围内自动执行。复用现有 DSH Host 插件，首轮在一个实际网站、一个账号验收，默认两个工作窗口。

使用流程：选择或编辑岗位配置 → 打开已登录招聘网站 → 开始 → agent 自动学习或复用网站配置 → 多窗口筛选与查看详情 → 符合条件的候选人立即进入打招呼队列 → 查看简单记录。用户可随时停止。首版先用推荐/搜索结果列表筛选，复杂站内筛选控件按实际需要学习。

网站无需人工填写 selector；从用户打开的已登录页面识别域名与页面结构。现有 fixtures 只复现了部分招聘卡片，自主适配效果和速度指标仍需用实际企业端页面确认；首轮真实验收页面尚未提供。

## 1. 根据现有代码需要改变什么

| 当前情况 | 对需求的影响 | 最小修改 |

| session 的活动 target/sessionId 会被切标签页改写 | 直接并发调用可能串页 | 每个窗口固定自己的 target 和执行上下文，同页串行、跨页并行 |
| 同 profile 可复用同一浏览器，缺少 worker 所有权 | 新 session 不等于独立窗口；恢复或关闭可能影响其他窗口 | 明确窗口归属，恢复只找自己的页面，关闭 worker 不结束共用浏览器 |
| 待审已按会话隔离（`Pacing` 的 `#pendings`），但额度仍按会话计数、锁仍按插件实例 | 一份任务授权要跨窗口共用，两次注册也要共用同一把锁 | 一份任务授权、账号总额度和候选人领取状态供所有窗口共用；锁按浏览器身份共享 |
| Journal 只有内存记录；本地数据根与守卫已存在（`lib/local.js`） | 重跑后无法可靠去重 | 记录写入已有的本地数据根，不另造存储路径 |
| 看板已是原生 DSH 页（`client.js`），有实时画面与逐条验证依据，但没有窗口级进度 | 用户看不到各窗口处理进度 | 在 `client.js` 里显示窗口状态、当前候选人、总数量和统一停止 |

依据：lib/act.js 的分阶段决策，lib/pacing.js 的 afterAction，cordis.patch.yml 的招聘预设，以及 lib/sessions.js 的切页、附加与回收逻辑。这些是当前代码事实，不是已经测得的处理速度。

## 3. 两份配置与自主适配

岗位配置单独保存在本地 JSON：岗位名称、职位描述、必须条件、偏好、排除条件、招呼文案或模板。运行时选择岗位版本，再设置联系上限和窗口数。同一岗位可用于不同网站，同一网站配置可服务不同岗位；修改岗位默认用于下一次运行，正在执行的任务固定使用启动时的版本。

网站配置单独保存在本地 JSON：域名、页面类型、布局特征、卡片与字段定位、稳定候选人标识、操作步骤、前后条件、结果反馈与版本。网站配置描述“怎么读取和操作”，岗位配置描述“筛选什么人”。

自主适配流程：

1. 缓存命中时，插件检查当前页面的定位与前后条件，然后直接复用配置。
2. 缓存不存在或失效时，招聘入口返回 needs_adaptation 和已保存进度；Host agent 自动调用结构检查模式，必要时查看截图，识别卡片、字段、按钮、弹窗及滚动容器。
3. agent 生成结构化网站配置；插件验证读取结果、定位唯一性、对象关联及操作前后条件。非发送操作可以试跑，首次实际招呼在原任务授权范围内核对，不新增逐人确认。
4. 验证通过后保存网站配置，两个窗口使用同一已验证版本，继续原任务。改版后只更新失效部分，不为每次点击重新学习。

最少增加的接口：新工具 `browser_inspect`（已实现），返回 snapshotId、有界 DOM 层级、已观察属性与逐项稳定性、跨页面的重复组、滚动容器和弹窗状态；一个网站配置工具负责 validate/save，招聘批处理入口负责执行与续跑。新增字段与工具需同步校验 Host schema。

### 3.1 定位语言与配置 schema（开工前置）

这是 agent 与插件之间唯一的契约：没有它，S1 既无法实现，也无法评审。开工前先定稿一页规格，至少写清五件事：

- **定位表达式是什么形式**：CSS selector、inspect 时由插件给节点盖的稳定标记，还是两者兼有。
- **卡片内的相对定位怎么写** —— 招聘页面最核心的需求（卡片边界、卡内按钮、卡内字段），也正是现有扁平快照做不到的部分。
- **inspect 的返回结构与有界预算**：层级深度、节点数、每节点保留的属性、总字符上限。一个招聘列表的 DOM 很容易上万 token，预算必须是一个明确数字。
- **配置的版本与失效字段**：什么变化算配置失效（域名、页面类型、布局特征、定位命中率），失效时返回什么、由谁更新。
- **动作类型枚举**：配置里允许出现的动作种类，与下方固定步骤列表一致。这个枚举同时是确认闸门的新判据（见 §1 表格第一行）。

规格已单独成文：[docs/SITE_CONFIG_SPEC.md](SITE_CONFIG_SPEC.md)。其中一条结论需要在这里重复：**配置声明只允许把动作升级进闸门，不允许降级放行** —— 否则等于让 agent 自己批改自己的作业。

规格定稿前不动 S1 的实现代码。

配置只允许插件实现的 read/click/type/select/scroll/wait 等固定步骤以及已观察节点的定位描述；不执行 agent 生成的 JavaScript。每次操作重新解析对象并核对条件，旧 ref 不能作为持久定位。截图已有，是否可供 agent 查看取决于 Host 路由的图片输入声明。

首版验证常见 DOM 页面自主适配，iframe、Shadow DOM、画布或无法确认语义的组件按实际网站补能力；不把“能自动学习”承诺成任意网站和任意改版都一次成功。适配失败先返回原因与进度，由 agent 更新配置；没有可靠目标时不猜测并发送。

## 4. 并行方式

- 复用一个已登录 Chrome，创建两个独立可见工作窗口，登录账号与 profile 共用。CDP 支持通过 Target.createTarget 的 newWindow 创建新窗口；已在本机 Chrome 实测：`newWindow: false` 得到 1 个窗口，`true` 得到 3 个窗口（以 `Browser.getWindowForTarget` 计数）。[官方协议定义](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json)
- 每个 worker 固定自己的 targetId 和 CDP sessionId；同一页面从读取到操作串行，其他窗口可以同时处理自己的候选人。不通过反复修改一个共享 session 的活动标签页来并行。
- 列表批量采集候选人 ID/详情 URL 后分配到队列；同一来源列表由固定拥有者翻页，其他窗口处理已领取候选人。实际网站若只支持列表内弹窗，则每个窗口按 agent 已学习且插件已验证的流程处理。
- 候选人被领取时立即占用，打招呼前再次检查共享记录和额度。profile 与招聘预设必须复用同一协调状态、写入服务与记录。
- 详情读取、字段提取和匹配判断并行；首版打招呼使用一个账号发送队列，读取窗口可在等待发送时继续筛选。窗口数不会自动倍增账号的联系额度和发送速度。
- 如果网站的职位切换等状态会影响其他窗口，相关切换串行协调；在真实网站验证窗口之间的状态隔离。
- 某个窗口关闭或失败，只恢复该 worker 的页面；释放 worker 不调用结束共用浏览器的路径。未决沟通仍保留记录，恢复时不重新发送。
- 默认从两个窗口开始；参数预留调整并发数，实际测试确认吞吐收益与网站行为后再增加到 3–4 个窗口。
- 窗口并行不会要求用户分别授权；暂停/继续仍使用原任务范围，统一停止会取消所有 worker 的新动作。
- 一个窗口负责首次学习或更新网站配置，其他窗口等待相关配置验证完成后复用；多个窗口不同时生成互相覆盖的规则。更新配置本身不改变原岗位和授权范围。
- 统一停止、单窗口暂停与人工接管见 S7：停止要贯穿采集、决策与发送队列，而不是只停住下一个动作；已提交到浏览器的动作保留为待核对，不宣称已回滚。
- 一次授权的边界同时是并行的边界：授权覆盖的动作种类之外，任何消耗额度的动作仍按原闸门逐次确认。授权失效（岗位或文案改动、网站配置版本更新、账号切换、上限调整、用户停止）后，所有窗口立即回到逐次确认。

## 5. 速度怎么提高

1. 列表一次读取多张卡片，先做明显的条件排除，只有需要补充资料时才打开详情。
2. 将候选人事实按文本预算分成小批次，利用现有 Jev 独立问题接口做匹配判断。不同候选人判断可以批量请求；有依赖关系的操作判断不能硬合并。
3. 已学习且验证过的按钮和组件由网站配置直接定位，按前置/后置条件执行；筛选主流程不再为每次点击重复请求“选动作、选目标、评级”。通用 browser_act 保留给原有调用与诊断。
4. 读取和本地判断不使用打招呼的随机间隔；导航、弹窗、输入和列表更新等待具体状态，并设置超时，减少页面已经就绪后的固定等待。
5. 账号发送单独控速，两个窗口共享发送许可和联系上限。先测量现有配置造成的等待，再根据实际网站反馈校准，不承诺窗口数与速度线性增长。
6. 候选人符合条件就进入发送队列，不等待整批筛选完成。限制预取队列长度，在联系上限达到或用户停止时结束采集。
7. 截图只用于当前选中窗口的查看与异常复核，避免为每个候选人生成整页截图。

速度验收记录三项：每分钟筛选人数、首个合适候选人的处理耗时、每分钟页面确认成功的打招呼人数。用同一网站、同一职位条件和同一批候选人比较单窗口与双窗口；分别报告模型耗时、页面等待和发送等待，再决定默认配置。尚未实测，不设虚假的固定吞吐承诺。

## 6. 记录保持简单

看板只需要一张表：候选人名称、简历链接、匹配结论、简短理由、打招呼状态和时间。窗口编号用于定位异常。底层保存网站/账号标识、候选人稳定 ID、本次任务、文案版本、操作意图与结果证据，支持去重。

使用一个本地 JSONL 文件，放在已有的本地数据根里（`lib/local.js`，见 §3.1 与 §1 表格新增行），所有 worker 通过单写入服务保存。领取、预留额度和写入意图须作为协调器的一段不可交叉的操作，防止两个窗口先后点击同一个人。写入失败停止相应沟通。测试记录与用户记录隔离。

打招呼状态区分待处理、已执行待核实、页面确认成功和明确失败。页面没有显示匹配条件时记为待核实；已经成功或发送结果不明的候选人不自动重发。简单记录不等于简历数据库，不默认保存整份简历或全部聊天内容。

## 7. 开发顺序与最小验收

1. **先定稿 §3.1 的定位语言与配置 schema**；随后用一个实际已登录网站验证结构检查 → agent 生成配置 → 插件校验与缓存的闭环；完成 S1 单窗口只读路径并测基线，不要求为该网站人工编写 selector。仓库与版本管理已就绪（Git、pre-commit 隐私扫描）。
2. 完成独立岗位配置、S2/S5，按选定条件批量筛选并形成简单记录；在本地复现页验证沟通与去重。
3. 完成 S3/S4，加入两个窗口、共享领取/额度与一次任务授权，在本地并发测试中验证正确性。
4. 完成 S6，实际网站试用单窗口和双窗口，按同批候选人比较速度，校准发送节奏。

复用现有 16 个套件（schema / labels / guardrails / regressions / guards / verify / concurrency / injection / privacy / inspect / site / posting / records / recruiting / control / workers，共 370 条断言），补实际页面 fixture、匹配断言、自主适配和并发场景；隐私扫描继续作为提交前的强制检查。重点检查：岗位更换与版本固定、缓存首次生成/复用、布局变化后自动更新、失效 ref、未知组件、同名对象、同一人被两窗同时发现、联系上限同时到达、窗口切页/关闭/恢复、单个 worker 结束、跨预设重复启动、停止/撤销、发送后超时及进程退出。新增入口与输出同时验证 Host schema。

### 第 2 步的验证现状（岗位配置 + S2 + S5）

**已用真实 Chrome 与本地 fixture 验证**（14 个套件 / 341 条断言，退出码全 0）：

- **岗位配置**：12 类拒绝；规则判定；**缺字段读作 unknown 而不是 fail**（否则会静默丢掉页面没描述的人）；偏好只记为理由、不会变成必须；存档损坏抛错并在列表中报告
- **记录**：写入前逐字段校验；并发追加不交叉；未决 / 已确认 / 已执行未确认**都阻止重发**，只有显式失败可重试；**重启后仍然阻止**（测试用新实例复现，而不是复用内存对象）；同一人在两个账号是两条记录；不可读的行抛错并指出行号
- **匹配**：只对规则定不了的候选提问；判定**合并成一次请求**；`not_shown` 与低置信度回答**都不改判定**；没有记录存储时拒绝放行而不是默认可以发
- **三者串成一条路径**：配置读取 → 规则判定 → 模型兜底 → 查记录去重；其中一条断言用**真实的记录存储**而非桩

**尚未做**：

- 把筛选暴露为 agent 工具（计划把招聘执行入口放在 S6）
- 发送与结果回写（S4）：`screen()` 只回答「谁该被联系、谁不该」，**目前没有任何调用方会真的发送**

**只有真实页面能回答的**：规则词表是否覆盖真实卡片的写法；一次批量判断在真实候选人文本上的准确性；模型判定在真实简历上的置信度分布是否与 0.7 的门槛相称。

### S1 的验证现状

**已用真实 Chrome 与本地 fixture 验证**（11 个套件 / 279 条断言，全部退出码 0）：

- 结构采集的每一项预算都在上限内，截断会上报；单次调用只能调低预算、不能调高
- 重复组与 repeats 能指出卡片所在；生成类名被过滤，不邀请调用方锚定它
- 配置格式的 13 类拒绝，包括存储的 ref、原始 CSS 字符串、任何未知键
- 卡片两阶段解析；卡内命中不唯一计入 ambiguous 并阻止发送，不退化成「第一个」
- marker 失效即 stale、报出是哪一条、且不解析任何卡片
- hitRate / ambiguous 门槛与 `canSend`；存档损坏时抛错而不是当作「没有配置」
- 只读读取路径：字段缺失读作未知，identity 未解析读作空

**只有真实登录页面能回答的**：

- `browser_inspect` 能否在站点的候选人列表上指出卡片组。**fixture 是按规格造的，它必然会过** —— 这不构成对真实页面的任何证据。
- 定位语言能否表达真实卡片：卡内相对定位、翻页、弹窗式沟通、以及站点的分页行为。
- 生成一条可用配置需要几轮往返、多少时间；真实页面的 hitRate 能否达到 0.9。

**前提**：Host 已连续运行 1 天余，本次新增的两个工具（`browser_inspect`、`browser_site_config`）**尚未加载**；上述验证需要先重启 Host。

首版通过条件：

- 根据用户给定的必须条件识别适合/不适合/待核实，并给出可复查的页面依据。
- 岗位和筛选条件可单独保存、切换，同一网站配置不写死职位要求。
- 首次页面适配由 Host agent 完成；缓存可以复用，预设布局变更后能够自动更新并继续原任务，正常执行不反复调用 agent 学习。
- 双窗口的读取与匹配确实重叠执行，目标页面相互独立；同一候选人只领取一次，已授权联系总数不超限。
- 一次开始授权后，符合者自动打招呼，用户无需逐人确认；当前阶段保留原有验证页面停手。
- 每条打招呼有对象与状态记录，超时后不自动重复发送；关闭一个 worker 不结束另一个。
- 统一停止后不再发起新沟通，已提交动作仍可核对结果。
- 用单/双窗口对照给出吞吐、首个结果耗时和失败率，确认提速没有降低对象与结果正确性。

本轮先交付插件中的“独立岗位配置 + agent 自主适配 + 双窗口筛选 + 自动打招呼 + 简单记录”。任务中心、多账号、多个独立浏览器进程和重启自动续跑以后再考虑。具体工期在首个实际网站的适配验证后估算；此文是开发计划，以上新能力尚未实现。
